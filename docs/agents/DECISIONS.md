# Decisions

Owned by `architect`. Other agents read it and never edit it. To challenge a decision, leave a message for `architect` on the board.

The owner can overrule any decision by editing it here. Agents follow whatever this file says.

Each decision uses this shape:

    ## ADR-NNN: <title>
    Status: proposed | accepted | superseded by ADR-MMM
    Context: the facts from this repo that matter
    Options: what was weighed, with the main trade-off of each
    Decision: what was chosen
    Consequences: what this makes easier and harder
    Checks: the exact commands agents run to verify work in this area

Android and ios work starts only from `accepted` decisions.

## ADR-001: Mobile stack
Status: accepted
Context: One person owns and runs Bachelor Point. The web is Next.js 14 with React and TypeScript, and almost every member opens it on a phone (`docs/meal-rate-on-mobile.md`). `system-design.md` already names React Native or Flutter for mobile. The android and ios agents run in a Linux cloud sandbox with Node 22 and npm, no macOS, no Xcode, no emulator and maybe no Android SDK, so every check they run must work on plain Linux. The board has separate android and ios agents, so whatever is chosen must let two agents work without stepping on each other.
Options:
- Native Kotlin and Swift: best platform fit, but two codebases in two new languages for one maintainer, every feature built twice, and Swift UI code cannot be compiled or tested on Linux, so the ios agent could verify nothing in its sandbox.
- Kotlin Multiplatform with native UI: shares logic, but the SwiftUI half still needs a Mac for every check and the build tooling is the heaviest of the options to keep running.
- Flutter: one codebase and `flutter analyze` and `flutter test` run on Linux, but Dart shares no code, types or tooling with the TypeScript web and adds a second language and SDK to maintain.
- React Native with Expo and TypeScript: one codebase in the language the owner already maintains, same npm tooling as the web, typecheck, lint and unit tests run on plain Linux, and EAS Build and EAS Submit build, sign and upload iOS and Android binaries in the cloud without a Mac.
Decision: React Native with Expo (managed workflow, Expo Router, TypeScript strict), one app for Android and iOS, built to `docs/agents/MOBILE-REFERENCE.md`. Pin Expo SDK 58, not the latest SDK, because the owner tests in Expo Go on an iPhone and Expo Go opens only the SDK it was built for; use exactly the package versions in the reference table and add packages only with `npx expo install`. Moving to a newer SDK is its own board task, raised only when the App Store's Expo Go moves. The app uses only modules that Expo Go bundles: no custom native code, no config plugin or library that needs a development build, and no committed `android/` or `ios/` folders. Native config lives in `app.config.ts`. `app.config.ts` reads the backend address from `MESS_API_URL` into `extra`; in development the sign-in screen shows the server address with a Change action, checks `GET /api/health` before saving, and keeps the address in `expo-secure-store`; production builds hide it. Plain `http://` is allowed only for an `http://` address in development; store builds use `https://`. The first and main test path is Expo Go on the owner's iPhone against the backend on the laptop over Wi-Fi; Android comes later on the same codebase. Store builds come later through EAS Build and EAS Submit with the `eas.json` profiles in the reference; the owner creates the Expo project, holds the Apple and Google accounts and EAS-managed signing credentials, and runs every `eas` command by hand. Nothing builds or releases from `agents/*`. UI text lives in the app's own locale file, the mobile counterpart of `src/lib/i18n/locales/en.ts`. The app talks to the backend only over the HTTP API defined by ADR-002 and does not import from the web `src/`.
Consequences: One codebase and one language for both stores, agents verify everything on Linux, and the owner can open every change in Expo Go with no Apple Developer account and no build. The price is the Expo Go module limit: a feature that needs a native module outside Expo Go (for example push notifications on iOS) needs a development build and an Apple account, so it is a deliberate board task and an owner decision, never a side effect. Both agents touch one codebase, so ADR-003 splits ownership by path to avoid conflicts. On-device testing happens only on the owner's phone, not in the sandbox. Agents never start EAS builds.
Checks: in the mobile app directory set by ADR-003: `npm ci --no-audit --no-fund && npx tsc --noEmit && npx eslint . && npx jest --ci && npx expo-doctor`. jest uses the `jest-expo` preset and `jest.setup.ts` mocks from MOBILE-REFERENCE.md; tests never call a real server. Agents never run `eas build`, `eas submit` or `expo prebuild`.

## ADR-002: Mobile sign-in and API contract
Status: accepted
Context: The web signs in through `POST /api/auth/login`, which sets the `bachelor_point_session` cookie. That cookie holds an HMAC-signed token from `src/lib/session.ts` (`uid`, `sv` = `User.tokenVersion`, `iat`, `exp`, 30 days, refreshed after 1 day). `getSessionUser` in `src/lib/auth-utils.ts` reads the token only from the cookie, checks `tokenVersion` and `status`, and about 80 API routes rely on it. `src/middleware.ts` returns 401 for any non-public `/api/*` request without a readable session cookie. `verifySessionToken` already rejects any payload that carries a `typ`, which is how impersonation tokens are kept apart. Errors are `{ error, ...extra }` from `src/lib/http.ts`. `GET /api/health` exists and is public. There is no OpenAPI file and no API versioning. A React Native app in Expo Go can store cookies only unreliably and is not a browser, so it sends no `Origin` and needs no CORS.
Options:
- Cookie sessions in the app: no backend change, but React Native cookie handling differs between iOS and Android and between Expo Go and store builds, and the token would not live in `expo-secure-store` as MOBILE-REFERENCE requires.
- Opaque tokens stored hashed in a new table: revocable per device, but needs a migration, a lookup on every request and admin screens, which is more for one person to run.
- Signed bearer token in the same format as the cookie token, with its own `typ`: reuses `session.ts` and the `tokenVersion` revocation the web already has, needs no migration, and cannot be swapped for a cookie token or an impersonation token because each verifier checks `typ`. The price is no per-device revocation: a lost phone is cut off by bumping `tokenVersion`, which signs the user out everywhere.
- For the API surface: a separate `/api/mobile/v1/*` copy of every route (clean versioning, but every feature built twice in the backend), versus the app calling the existing `/api/*` routes under a contract that only allows additive change.
Decision:
- Token: `src/lib/session.ts` gains `createMobileToken(userId, tokenVersion)` and `verifyMobileToken(token)`, the same signed format with `typ: 'mob'`, 30-day `exp`. `verifySessionToken` and `verifyImpersonationToken` stay as they are, so cookie, impersonation and mobile tokens never verify as one another.
- Reading it: `getRealSessionUser` in `src/lib/auth-utils.ts` uses the cookie when present, exactly as today. Only when there is no session cookie does it read `Authorization: Bearer <token>`, verify it with `verifyMobileToken` and load the user with the same `loadActiveUser` check. A bearer request never sets cookies, never adopts an identity cookie and never applies impersonation. `src/middleware.ts` lets an `/api/*` request through when the bearer token's claims read as `typ: 'mob'` and unexpired, mirroring `readSessionClaims`; the route still verifies the signature. Pages, not under `/api/`, ignore bearer tokens.
- Sign-in routes, new and mobile-only, under `/api/mobile/v1/auth/` and public in the middleware: `POST login` with `{ email, password }` returns `{ token, expiresAt, user: { id, name, email, role } }` and sets no cookie; `POST refresh` with a valid bearer token returns a new `{ token, expiresAt }`; `POST logout` ends the activity session and returns `{ ok: true }` (the app then deletes its token). The credential checks, lockouts, `recordLoginAttempt`, rehash and `touchSession` of `src/pages/api/auth/login.ts` move into one shared function in `src/lib/` that both login routes call, so the web route's behaviour and responses do not change. A mobile login records its activity session with device `APP`. Sign out everywhere stays `tokenVersion` increment.
- Data routes: the app calls the existing `/api/*` routes with the bearer header. No route is copied. The routes the app uses are listed in the contract below, and a listed route may only change additively: new optional request fields, new response fields. Removing or renaming a field, changing its type or meaning, or tightening validation of a listed route needs a new route path and an ADR. `/api/mobile/v1/` holds only what has no web counterpart.
- Contract: `docs/api/mobile-openapi.json`, OpenAPI 3.1 written by hand, lists each route the app uses with request and response schemas and the shared error shape `{ error: string }`. A route enters the file in the same change that makes the app call it. `scripts/check-openapi.js` checks without a database that the file parses, every path maps to a file under `src/pages/api/`, every operation has a 2xx response, and every path under `/api/mobile/` is public in `src/middleware.ts` only if it is under `/auth/`. The app writes its zod schemas from this file by hand; no code generation.
- Errors and status: unchanged `src/lib/http.ts` shapes. 401 means sign in again: the app tries `refresh` once, then returns to sign-in. 429 carries `Retry-After`.
- Transport: no CORS headers are added. `http://` only as ADR-001 allows. The token lives only in `expo-secure-store`.
Consequences: The web cookie flow, its responses and its pages stay unchanged, and one backend serves both clients with the same permission checks. Backend work is small: two functions in `session.ts`, a bearer fallback in `auth-utils.ts` and the middleware, three routes, the shared login function, the contract file and its check. The app cannot be signed out per device; that needs a later ADR with a token table if it becomes a problem. Because data routes are shared, a web change to a listed route can break the app; `check-openapi.js` catches missing paths, not changed fields, so whoever changes a listed route updates the contract in the same commit and the qa agent checks it.
Checks: backend: `npm ci --no-audit --no-fund && npm run typecheck && npm run lint && node scripts/check-allocation.js && node scripts/check-openapi.js && node scripts/check-mobile-auth.js`, where `check-mobile-auth.js` signs and verifies tokens without a database and proves a cookie token, an impersonation token and a mobile token each fail the other verifiers and that an expired or tampered mobile token fails. Mobile: the ADR-001 checks, with tests against a mocked fetch that follows `docs/api/mobile-openapi.json`.

## ADR-003: Mobile repo layout, path ownership and checks
Status: accepted
Context: ADR-001 makes one Expo app for both platforms, and the owner tests on an iPhone in Expo Go first, Android later (board message on A3, `docs/agents/MOBILE-REFERENCE.md`). The web root has its own `package.json` (no `workspaces`), `tsconfig.json` that includes only `src/**`, and `.eslintrc.json` (ESLint 8, `next lint`, which lints only the root `src/`, `pages/`, `app/`, `components/` and `lib/`). The `Dockerfile` builder runs `COPY . .` and `.dockerignore` does not exclude any app folder. `deploy.yml` runs on every push to `develop`, whatever path changed. Two agents, android and ios, work on the same codebase in parallel and must not edit the same files in the same run.
Options:
- npm workspaces or a monorepo tool shared with the web: one install, but it changes the web's install and lockfile, makes Metro resolve through the root `node_modules`, and couples the deploy to mobile packages.
- Separate repository: cleanest isolation, but the board, the ADRs and the OpenAPI contract live here, so every task would span two repos and two sets of credentials.
- A standalone app folder `mobile/` in this repo with its own `package.json` and lockfile and no root workspace: web and app stay independent, agents and the contract stay in one place. The price is two installs.
- For ownership: split by platform folder (impossible, ADR-001 forbids `ios/` and `android/` folders, and almost all code is shared), versus one lead owner for shared code with each feature folder owned by the board row that builds it.
Decision:
- The app lives in `mobile/`, a standalone Expo project with its own `package.json`, `package-lock.json`, `tsconfig.json` (extends `expo/tsconfig.base`, `strict`, `@/*` -> `./src/*`), `eslint.config.js` (flat config from `eslint-config-expo`), `jest.setup.ts`, `app.config.ts` and `.gitignore` (`node_modules/`, `.expo/`, `dist/`, `web-build/`, `*.jks`, `*.p8`, `*.p12`, `*.key`, `*.mobileprovision`, `.env*`). The root `package.json` gets no `workspaces` and no mobile scripts. Nothing in `mobile/` imports from the root `src/`, and nothing in the root imports from `mobile/`.
- Inside `mobile/`, the layout of MOBILE-REFERENCE: `src/app/` routes only (`(auth)/`, `(app)/`, `_layout.tsx`), `src/features/<feature>/` screens, hooks, zod schemas and `*.spec.tsx` beside them, `src/core/` (`config`, `storage`, `api` for the fetch client and bearer handling of ADR-002, `providers`, `theme`, `i18n`). UI text lives in `src/core/i18n/en.ts`, one top-level key per feature. Platform differences use `*.ios.tsx` / `*.android.tsx` files or `Platform.OS`, never separate folders.
- Ownership. ios is the lead, because the iPhone is the first test device: ios owns `mobile/` as a whole, in particular the shared files `package.json`, `package-lock.json`, `app.config.ts`, `tsconfig.json`, `eslint.config.js`, `jest.setup.ts`, `src/app/_layout.tsx`, `src/app/(auth)/_layout.tsx`, `src/app/(app)/_layout.tsx` and `src/core/**`. android owns `mobile/src/**/*.android.ts(x)`, `mobile/config/android.ts` (the `android` block that `app.config.ts` spreads in) and `docs/mobile-on-android.md`. A feature folder `mobile/src/features/<feature>/` and its route files belong to the agent whose board row builds it, and the row names the folder. Either agent may add its own feature's keys to `src/core/i18n/en.ts`; on a rebase conflict there keep both sides. When android needs a change in a file ios owns (a new package, a `core` change), it leaves a message for ios or a row owned by ios, and does not edit the file. The backend side (`src/`, `prisma/`, `scripts/`, `docs/api/mobile-openapi.json`) stays with fixer; an app agent that needs a new route or a contract change adds a fixer row.
- Order: ios scaffolds `mobile/` (I1) and owns sign-in. android starts once the scaffold is on `agents/integration`: its first task is the Android pass on the same app (Expo Go on Android, `config/android.ts`, `*.android.tsx` fixes), not a second scaffold. A5 rewrites D1 to match.
- Web isolation: the root `.dockerignore` excludes `mobile` so the backend image never copies the app. Root `tsconfig.json` and `next lint` already skip `mobile/`; nobody widens their `include` or lint dirs to cover it.
Consequences: The web install, build and deploy stay exactly as they are, and the app can move to its own repo later by moving one folder. Each agent edits disjoint files in a run, with the shared files behind one owner, so android depends on ios for package and core changes and may wait a run for them. Two `npm ci` runs per full check. A mobile-only commit merged to `develop` still triggers `deploy.yml`; ADR-004 decides path filters.
Checks: mobile, run by android and ios from `mobile/`: `npm ci --no-audit --no-fund && npx tsc --noEmit && npx eslint . && npx jest --ci && npx expo-doctor`. If `expo-doctor` fails only for lack of network, say so in the row note and do not skip the other checks. Then from the repo root, to prove the web is untouched: `npm ci --no-audit --no-fund && npm run typecheck && npm run lint`. Backend changes keep the ADR-002 checks.

## ADR-004: CI/CD, Docker and release lanes
Status: accepted
Context: The live path is `.github/workflows/deploy.yml`: every push to `develop` (and any `workflow_dispatch`, from any branch the dispatcher picks) runs `scripts/deploy.sh` on the self-hosted runner `[self-hosted, bachelor-point]`, which builds the root `Dockerfile` (node:20-alpine, Next standalone), imports the image into k3s, applies `k8s/free-tier` over `k8s/base`, runs `k8s/base/migrate-job.yaml` and switches blue-green with `scripts/blue-green.sh`. `ops.yml` is manual k3s maintenance on the same runner. There is no CI at all: nothing runs the typecheck, lint or `scripts/check-*.js` on `agents/*`, and a broken image is first seen in production. `.dockerignore` already drops `docs`, `*.md`, `k8s`, `terraform`, `Jenkinsfile` and `.github`, but not `mobile` (F21) or `.claude`. Stale, not on the deploy path: `Jenkinsfile` (ECR and EKS `bachelor-point-prod`), `terraform/*.tf` at the root (EKS; `docs/DEVOPS-FREE-TIER.md` section 2 says tear it down) and `k8s/production` (ingress and HPA for EKS); `terraform/free-tier` and `k8s/free-tier` are live. The repo is public, so GitHub-hosted runner minutes are free and a workflow must never put a pull request or an `agents/*` push on the self-hosted runner. ADR-001 keeps every `eas` command with the owner, and the app has no native code.
Options:
- Keep no CI and rely on agents running checks in the sandbox: nothing to maintain, but nothing proves the image builds or that a merge to `agents/integration` still passes, and qa cannot see a red build.
- Jenkins, as `Jenkinsfile` and DEVOPS-FREE-TIER option A describe: one more server for one person to run, and the file targets an EKS cluster that no longer exists.
- GitHub Actions CI on GitHub-hosted Linux runners for `agents/**` and pull requests, with the existing `deploy.yml` left as the only deploy and narrowed: no new infrastructure, free on a public repo, and the same commands agents run in the sandbox.
- For mobile: EAS Workflows or an Actions job that runs `eas build` with an `EXPO_TOKEN` secret (automatic store builds, but a token in the repo's secrets and builds from branches the owner did not review), versus EAS builds by the owner by hand and only JS-level checks in CI. A macOS runner adds nothing while the app has no native code and no committed `ios/` folder.
Decision:
- CI: new `.github/workflows/ci.yml`, `on: push` to `agents/**` and `pull_request` to `develop`, `paths-ignore` `docs/**` and `**/*.md`, `permissions: contents: read`, `concurrency` per ref with `cancel-in-progress: true`, `runs-on: ubuntu-latest` only, no secrets. Job `backend` (Node 20, as the image): `npm ci --no-audit --no-fund`, `npm run typecheck`, `npm run lint`, then every `scripts/check-*.js` that exists, each with `node`. Job `image`: `docker build .` with no push and no tag outside the runner, which proves `deploy.sh` can build it. Job `mobile` (Node 22), only when `mobile/package-lock.json` exists (a first step tests the file and later steps use its output): from `mobile/` the ADR-003 checks, then `npx expo export --platform ios --platform android --output-dir dist` to prove Metro bundles both platforms without a native SDK. `expo-doctor` may fail only for network, as ADR-003 says; elsewhere a red job is a failed check.
- Deploy: `deploy.yml` stays the only workflow that deploys and the only one on the self-hosted runner besides `ops.yml`. It gains `paths-ignore` `mobile/**`, `docs/**`, `**/*.md` and `.claude/**` on the push trigger, so app-only or docs-only squashes do not rebuild production, and a job-level `if: github.ref == 'refs/heads/develop'`, so a `workflow_dispatch` from `agents/*` or any other branch cannot deploy. `ops.yml` gets the same `if`. Nothing else in the deploy path changes: same `deploy.sh`, `blue-green.sh`, `k8s/free-tier`, migrate job and rollback with `./scripts/deploy.sh --rollback`.
- Backend image: the root `Dockerfile` stays as it is. `.dockerignore` adds `mobile` (F21) and `.claude`. A Node major bump in the image is its own board task, and CI's backend Node follows the image.
- Mobile release: no workflow ever runs `eas`. The owner runs, by hand from a reviewed `develop` checkout: `eas build --profile preview` for test builds, `eas build --profile production --platform ios|android` then `eas submit` for the stores. iOS signing uses EAS-managed credentials on the owner's Apple Developer account, Android uses the EAS-managed upload keystore; no signing file, `EXPO_TOKEN` or store key goes into the repo or its secrets. `cli.appVersionSource: remote` with `autoIncrement` keeps build numbers on EAS. Day-to-day testing stays Expo Go per ADR-001.
- Stale files: agents do not build on or edit `Jenkinsfile`, the root `terraform/*.tf` or `k8s/production`. Whether to delete them is an owner decision; until then they stay untouched.
- Ownership: fixer owns `.github/workflows/`, `Dockerfile` and `.dockerignore`. qa reads the `ci.yml` result of a branch before merging it and records a red run on the board instead of merging.
Consequences: Every work branch gets the same checks agents run, plus an image build, on free runners, with no secrets and no path to production. Production deploys only from `develop`, and fewer of them. The mobile JS bundle is proven on Linux, but native build problems surface only when the owner runs EAS. A workflow change merged to `develop` takes effect on the next run, so a mistake in `deploy.yml` can stop deploys; fixer keeps that change to the two lines above. The stale files keep confusing readers until the owner removes them.
Checks: workflows: `npx --yes @action-validator/cli@0.6.0 .github/workflows/ci.yml` and the same for `deploy.yml` and `ops.yml`, plus `node scripts/check-workflows.js`, which parses every workflow without network and fails if any job outside `deploy.yml` and `ops.yml` uses a `self-hosted` runner, if `deploy.yml` or `ops.yml` lacks the `refs/heads/develop` guard, if `deploy.yml` triggers on anything but `develop` and `workflow_dispatch`, or if any workflow contains `eas build` or `eas submit`. After pushing, the branch's `ci.yml` run on GitHub must be green; read it with the GitHub tools. Backend and mobile checks as ADR-002 and ADR-003.

## ADR-005: Mobile feature plan, navigation and build order
Status: accepted
Context: The app has sign-in (I1, I3) and a member dashboard (I5), on a single `Stack` in `mobile/src/app/(app)/_layout.tsx`. The web covers meals with past-day edit requests and supervisor approvals (`docs/meal-edit-approvals.md`), meal prompts and quick reply (`docs/meal-prompts.md`), bazar duty and expenses, bills and collections, payments, advances and dues, settlement, final settlement and month closing, members, invitations, supervisors and co-supervisors, in-app notifications with Web Push (`/api/push/subscribe` takes a VAPID `endpoint` and `keys`, which a native app does not have), profile and settings, and admin pages. The contract `docs/api/mobile-openapi.json` lists only health, the three mobile auth routes, `GET /api/groups` and `GET /api/reports/dashboard`. No route the app needs uses multipart upload. Money rules have open fixer rows (F7-F18, F29-F35), so numbers can still change on the server.
Options:
- Copy each web page one to one as a screen: familiar to members, but the web pages are wide tables and many screens would ship before the owner can test any.
- Build by user role (all member screens, then all supervisor screens): simple to describe, but a supervisor could not test meals end to end until the very end.
- Build by feature, in the order a member uses the app daily, each feature as a vertical slice: contract row (fixer), shared screen with member and supervisor actions (ios), Android pass (android). The owner can test one finished feature on the iPhone after every few runs.
Decision:
- Navigation: `(app)/_layout.tsx` becomes bottom tabs with Expo Router `Tabs` (bundled in Expo Go): Home (dashboard and quick reply), Meals, Money (bazar, bills, payments as a segmented screen), Mess (members, invitations, settlement and closing), More (notifications, profile, settings, admin, sign out). Detail screens are stack routes inside each tab folder, `src/app/(app)/<tab>/`. The active group comes from `GET /api/groups` in a new `src/core/providers/group.tsx`, shown as a picker in the header only when the user has more than one group.
- Order, each feature fully usable before the next: shell, meals, meal approvals, quick reply, bazar and duty, bills and collections, payments and dues, settlement and closing, members and invitations, notifications, profile and settings, supervisor dashboard, admin. Android passes follow each group of features.
- Per feature: a fixer row adds the routes the screen calls to `docs/api/mobile-openapi.json` (contract only; a route that needs a change is its own fixer row), then an ios row builds `mobile/src/features/<feature>/` with zod schemas from the contract and Jest tests on mocked fetch, then an android row does `*.android.tsx` fixes only. Supervisor and admin actions live in the same feature folder as the member view and show only when the server says the user may act (role from `auth/me` or the route's own flags); a 403 shows the server's `error`. The app never computes money: rates, shares, dues and balances are shown as the server returns them.
- Out of this plan: remote push to the phone (needs an ADR on Expo push tokens, a backend table and sender, and whether Expo Go can receive them; A7), community posts and to-let, newsletter, impersonation and admin activity drill-downs. Notifications ship as an in-app list with an unread badge, refreshed on focus.
- The full row list and the screens each row builds are in `docs/agents/notes/A6.md`.
Consequences: The owner gets a testable feature roughly every three runs, and android never waits on more than one ios row. The contract grows one feature at a time, so `check-openapi.js` stays meaningful. Until A7 is decided, members learn of approvals and changes only when they open the app. Money screens may show different numbers after F-row fixes land; that is expected and not an app bug.
Checks: as ADR-003 for mobile rows and ADR-002 for contract rows (`node scripts/check-openapi.js` included).

## ADR-006: Remote push to the mobile app
Status: accepted
Context: Web Push lives in `src/lib/push.ts`: `sendPushToUser(userId, payload)` sends VAPID messages to every `PushSubscription` row (`endpoint`, `p256dh`, `auth`) and deletes a row on 404 or 410. Its only caller is `src/pages/api/bazar-duty/dispatch.ts`. Every in-app notification goes through `notifyUsers` in `src/lib/notifications.ts`, which writes the `Notification` rows and sends email fire-and-forget, gated by `isNotificationEnabled(type)` (the admin switches of `docs/notification-settings.md`) and `actorIsAdmin`. `/api/push/subscribe` needs a browser `endpoint` and `keys`, which a native app does not have. ADR-001 keeps the app inside Expo Go on the owner's iPhone with no paid Apple account, and every `eas` command with the owner. `expo-notifications` is bundled in Expo Go. Since SDK 53, Expo Go on Android cannot receive remote push at all, and Expo Go on iOS can, through Expo's own push credentials. `getExpoPushTokenAsync` needs the EAS `projectId` of an Expo project, which only the owner can create. The sandbox could not reach docs.expo.dev on this run, so the ios row re-reads the SDK 58 `notifications` page before building.
Options:
- Web Push from the app: no backend change, but React Native has no service worker or VAPID endpoint, so it cannot work.
- Direct APNs and FCM from the backend: no third party in the path, but it needs an Apple Developer account and APNs key and a Firebase project before the first test, two credential sets for one person to rotate, and it does not work in Expo Go.
- Expo push service: the app gets an `ExponentPushToken[...]` from `expo-notifications`, the backend posts to `https://exp.host/--/api/v2/push/send` with plain `fetch` and no SDK. Works in Expo Go on iOS today with only a free Expo project; store builds later need the APNs key and FCM key uploaded to EAS by the owner, with no backend change. The price is that notification titles and bodies pass through Expo, Apple and Google, and Android needs a development or store build to receive anything.
- For what gets pushed: only bazar duty (as Web Push today) versus every in-app notification. The app's notification list is the in-app bell, so a push per bell entry is what members expect, and the admin switches already decide which types exist.
Decision:
- Service: the Expo push service. No `expo-server-sdk`; `fetch` only.
- Table: new `MobilePushToken` (`id` uuid, `userId` -> `User` cascade, `token` unique, `platform` `ios` | `android`, `createdAt`, `updatedAt`, `lastSeenAt`), `@@index([userId])`, by a new migration file only. `PushSubscription` stays untouched.
- Routes, mobile-only because the web has no counterpart, bearer or cookie session required, not public in the middleware: `POST /api/mobile/v1/push/register` with `{ token, platform }` upserts by `token`, moves it to the caller if another user held it, sets `lastSeenAt`, returns `{ ok: true }`; `POST /api/mobile/v1/push/unregister` with `{ token }` deletes the caller's row and returns `{ ok: true }` even if none existed. A token that does not match `^(ExponentPushToken|ExpoPushToken)\[.+\]$` is a 400. Both go into `docs/api/mobile-openapi.json` in the same change.
- Sender: new `src/lib/expo-push.ts` with `sendExpoPushToUsers(userIds, { title, body, data })`. It loads the rows, posts in chunks of 100 with `Accept: application/json` and, when `EXPO_ACCESS_TOKEN` is set, `Authorization: Bearer` (read through `pushConfig` in `src/config/index.ts`; optional, for Expo's enhanced security). It reads the tickets and deletes a row whose ticket error is `DeviceNotRegistered`. It never throws, never awaits receipts and never retries; a lost push is acceptable because the bell already holds the notification. `data` is `{ link, type, groupId }` with `link` as stored on the notification.
- Wiring: `notifyUsers` sends the Expo push fire-and-forget beside email, after the same `isNotificationEnabled` and `actorIsAdmin` checks, title from the notification title and body from its excerpt trimmed to 180 characters. The bazar duty dispatch keeps its `sendPushToUser` call for Web Push; it already goes through `notifyUsers`, so the app receives it once. Web Push is not widened to every notification by this ADR.
- App: `expo-notifications` added by ios with `npx expo install`. After sign-in, only when `Platform.OS === 'ios'` or the app is not running in Expo Go (`Constants.executionEnvironment`), and only when `extra.eas.projectId` is set from the env var `EXPO_PROJECT_ID` in `app.config.ts`, it asks permission once, gets the token with that `projectId` and calls `register`. If any of that is missing or refused, it skips quietly; the in-app list still works. Sign out calls `unregister` before the auth `logout`. A tap on a push opens the screen for `data.link` when the app has one, otherwise the notifications list. Foreground pushes show a banner and invalidate the notifications query. No `expo-notifications` config plugin goes into `app.config.ts` until the owner asks for store builds. Android gets a `default` notification channel in an `*.android.ts` file.
- Owner actions, not agent work: create the free Expo project (`eas init`) and set `EXPO_PROJECT_ID` locally for Expo Go on the iPhone; optionally set `EXPO_ACCESS_TOKEN` on the server. For store builds later: an Apple Developer account and APNs key, and a Firebase project with an FCM V1 service-account key, both uploaded with `eas credentials`. None of these files is committed.
Consequences: The owner can test remote push on the iPhone in Expo Go with only a free Expo account and no Apple account. Android members get push only after the owner makes a development or store build. One backend sender serves both platforms, and store builds need no backend change. Notification text leaves our server through Expo, Apple and Google, so it must keep the current rule of names and short excerpts, never balances beyond what the bell already shows. No per-device push settings: a member stops push by refusing permission or in iOS Settings, and the admin switches stop it for everyone. Receipts are not checked, so a token rejected by Apple or Google only after the ticket stays until its next `DeviceNotRegistered`.
Checks: backend: the ADR-002 checks plus `node scripts/check-expo-push.js`, which transpiles `src/lib/expo-push.ts` like `check-mobile-auth.js` does, stubs `fetch` and the Prisma calls, and proves chunks of 100, the optional bearer header, deletion on `DeviceNotRegistered` only, and that a rejected `fetch` does not throw. Mobile: the ADR-003 checks, with `expo-notifications` mocked in `jest.setup.ts`; tests prove registration is skipped without a `projectId` and on Android in Expo Go, and that sign out unregisters before logout.

## ADR-008: Logging and tracing across web, API and mobile
Status: accepted
Context: The backend has almost no logging: `withAudit` in `src/lib/with-audit.ts` wraps 91 of the 92 API routes (not `live.ts`) and prints one `console.error` on a thrown handler; `src/lib/bootstrap/index.ts` has the only other `console.error`. No request id exists anywhere. `withAudit` already opens an `AsyncLocalStorage` context (`runWithActor` in `src/lib/audit.ts`), but it reads only the cookie session, so mobile bearer requests run with `actorId` null and their rows miss `createdById`/`updatedById`. `src/middleware.ts` returns 401 for unsigned API calls before `withAudit` runs, so those leave no trace. The web client goes through `apiRequest` in `src/lib/api-client.ts`; the app through `send`/`request` in `mobile/src/core/api/client.ts` (ios-owned per ADR-003). Production runs on k3s in namespace `bachelor-point` with label `app=bachelor-point` (`scripts/deploy.sh`, `scripts/blue-green.sh`); local and owner testing use `docker-compose.yml` (`app`, `cron`), which sets no log options. The owner tests on iPhone, Android and web and wants every failure in one stream Claude can follow.
Options:
- pino or winston: mature, fast, but a new dependency, transports that fight the Next.js bundler, and no Edge runtime support for the middleware.
- A hosted log service (Sentry, Logtail, Grafana Cloud): search and alerts, but an account, a key and a bill for one person, and data leaves the server.
- A small in-repo JSON-lines logger on stdout: no dependency, works in Node and Edge, the container runtime already captures and rotates stdout, and `docker compose logs -f` or `kubectl logs -f` is the live stream. No search beyond grep and a filter script; logs live only as long as container log rotation keeps them.
- Request id from the middleware for every path versus from `withAudit` for API routes only: the middleware would need every `NextResponse.next()` rewritten to forward headers; API routes are where failures happen.
Decision:
- Logger: new `src/lib/log.ts`, no dependency. `log.debug|info|warn|error(event, fields?)` writes one JSON line to stdout: `{ ts, level, event, src, rid, uid, ...fields }`. `event` is a dotted name such as `api.end` or `fn.error`; `src` is `api` on the server or the client platform; `rid` and `uid` come from the request context when present. Errors serialise as `{ name, message, stack }`, stack cut to 20 lines. Level from `LOG_LEVEL` (`debug|info|warn|error`, default `info`) through a new `logConfig` in `src/config/index.ts`. Never throws. The two existing `console.error` calls move to it. `scripts/cron-loop.js` prints the same line shape by hand with `src: cron`.
- Redaction, in `log.ts` and applied to every field and every client entry: any object key whose lower-cased name contains `password`, `token`, `secret`, `authorization`, `cookie`, `otp`, `apikey`, `p256dh` or is exactly `auth` or `code` gets `"[redacted]"`; strings over 500 characters are cut, arrays keep 20 items, depth stops at 6, and any string matching `Bearer \S+` has the token replaced.
- Request id: `withAudit` takes `x-request-id` from the request when it matches `^[A-Za-z0-9._-]{8,64}$`, otherwise makes one with `crypto.randomUUID()`, sets it as the `x-request-id` response header, and stores it beside `actorId` in the existing `AsyncLocalStorage` context (`getRequestId()` added to `audit.ts`). `withAudit` resolves the actor from the cookie session or, when there is no cookie, the mobile bearer token, which also fixes the missing audit stamps on mobile writes.
- API logging in `withAudit`: `api.start` (info) with `method`, `path` (query values whose key would be redacted are redacted), `uid`, `ip`, `ua` cut to 120 characters, and the redacted JSON body, cut to 2 KB, or only `contentType` and `bytes` for multipart; `api.end` with `status` and `ms`, at `info` below 400, `warn` for 4xx, `error` for 5xx; `api.error` (error) with the error when the handler throws. Rate-limit and payload rejections log `api.end` too. The middleware logs `api.denied` (warn) with `method` and `path` before returning its 401.
- Lib tracing: `traced(name, fn)` in `log.ts` wraps an async or sync function and logs `fn.start` (debug, redacted args), `fn.end` (info, `ms`, and a result summary: the `id` and `status` fields when present, otherwise the type), and `fn.error` (error, `ms`, error) and rethrows. It is applied at the export of the functions that write or compute money, auth and membership: `bills.ts`, `bill-collections.ts`, `advances.ts`, `settlement.ts`, `final-settlement.ts`, `closings.ts`, `expense-items.ts`, `meal-cost.ts`, `login.ts`, `password.ts`, `password-tokens.ts`, `user-sessions.ts`, `login-attempts.ts`, `groups.ts`, `supervisors.ts`, `role-requests.ts`, `user-permissions.ts`, and the payment and member handlers' lib calls they reach. Pure formatters and getters called in loops are left out.
- Client log endpoint: `POST /api/logs`, public in the middleware so failures before sign-in arrive, wrapped in `withAudit` for its per-IP write limit and body cap, `maxRequestBodyBytes` 32 KB. Body `{ platform: 'web'|'ios'|'android', appVersion?, entries: [{ ts, level, event, rid?, msg?, data? }] }`, at most 50 entries, `msg` cut to 1000 characters. Each entry is redacted again and re-emitted as one line with `src` = `platform`, `client: true`, the client `rid` and `ts` kept as `clientTs`, and `uid` from the session or bearer when one is valid. Entries below `LOG_LEVEL` are dropped. Returns `204`; a bad body is a 400. Goes into `docs/api/mobile-openapi.json` in the same change.
- Web client: new `src/lib/client-log.ts` buffers entries and flushes to `/api/logs` every 5 s, at 20 entries, at once on `error`, and on `pagehide` with `navigator.sendBeacon`. It records `window.onerror`, `unhandledrejection`, and from `apiRequest` every network failure and every 5xx with `method`, `path`, `status` and the response `x-request-id`. It never reports its own failed flush. Mounted once in `_app`.
- App: ios adds `mobile/src/core/log/` with the same buffer and flush rules, posting with plain `fetch` to `${baseUrl}/api/logs` and `platform` from `Platform.OS`. `send` in `client.ts` sends an `x-request-id` (16 random hex characters) on every call and logs `api.call` (info, `method`, `path`, `status`, `ms`, `rid`), `api.fail` (warn for 4xx, error for 5xx and network). It also records `ErrorUtils.setGlobalHandler` (chaining the previous handler), the React Query `QueryCache` and `MutationCache` `onError`, and the root error boundary. In `__DEV__` each entry also goes to `console` for Metro. A flush failure drops the batch quietly; the buffer holds at most 200 entries. The token, request bodies and response bodies are never logged by the app.
- Where logs go and how to follow them: stdout of the `app` and `cron` containers only; no file, no database table, no third party. `docker-compose.yml` gives `app` and `cron` `logging: { driver: json-file, options: { max-size: 10m, max-file: "5" } }` and `LOG_LEVEL: "${LOG_LEVEL:-info}"`; the k8s app deployment gets `LOG_LEVEL` too. Follow live with `docker compose logs -f app cron`, or in production `sudo k3s kubectl -n bachelor-point logs -f -l app=bachelor-point --prefix --max-log-requests 10`. New `scripts/log-view.js` reads that stream on stdin, passes non-JSON lines through, and filters with `--level warn`, `--rid <id>`, `--uid <id>`, `--src ios|android|web|api|cron` and `--event <prefix>`, printing one compact line per entry. Claude follows it from a Claude Code session on the owner's machine with `docker compose logs -f app | node scripts/log-view.js --level warn` under the Monitor tool; the cloud sandbox cannot reach the server. How-to in new `docs/LOGGING.md`.
Consequences: One stream holds web, iPhone, Android, API and cron, joined by `rid` from the client call to the server lines it caused. No new dependency or service to run. Logs are lost when the container log rotates or a pod is replaced, so this is for live testing and recent incidents, not an audit trail; the audit stamps and history tables stay the record. Logging every request at `info` makes the stream busy; the owner sets `LOG_LEVEL=warn` when it is too noisy. `/api/logs` is public, so anyone can write lines into the log; the per-IP limit and size caps bound it, and client lines are marked `client: true` so they are never mistaken for server facts. Request bodies are logged after redaction, so any new secret field must use one of the redacted key names.
Checks: backend: the ADR-002 checks plus `node scripts/check-logging.js`, which transpiles `src/lib/log.ts` like `check-mobile-auth.js` does, captures stdout, and proves one parseable JSON line per call, level filtering by `LOG_LEVEL`, redaction of every listed key at any depth and of `Bearer` strings, the string, array and depth caps, that `traced` logs `fn.end` with `ms` and `fn.error` and rethrows, that the logger never throws on a circular object, and the `x-request-id` accept-or-replace rule. Web reporter and `/api/logs`: the same script also checks the entry validator (50-entry cap, unknown platform rejected). Docker: `docker compose config -q` when `docker` exists, otherwise say so in the row note. Mobile: the ADR-003 checks, with tests against a mocked `fetch` proving every call sends `x-request-id`, logs `api.call`, never includes the bearer token in an entry, flushes to `/api/logs`, and that a rejected flush neither throws nor logs itself.
